Thiossane Store — Documentation Backend

Guide d'onboarding pour toute personne qui rejoint le projet. Objectif : comprendre en 20 minutes comment le code est organisé, pourquoi il est organisé ainsi, et où aller pour ajouter une fonctionnalité sans casser la sécurité existante.

1. C'est quoi, ce projet ?

Une marketplace de jeux vidéo (façon itch.io), pensée pour le marché sénégalais :

  • Les joueurs parcourent un catalogue, achètent ou téléchargent des jeux gratuits, laissent des avis, mettent des favoris.
  • Les développeurs/studios publient des jeux, gèrent leurs versions (par plateforme), passent par une modération avant publication.
  • Les administrateurs modèrent les jeux, gèrent les comptes et les réglages système.
  • Le paiement se fait par mobile money (Wave, Orange Money, YAS), en francs CFA (XOF), avec confirmation asynchrone par webhook.

Règle d'or du projet : si une ressource peut être décrite comme du CRUD standard avec des règles d'autorisation simples, elle est modélisée en #[ApiResource] directement sur l'entité (Doctrine + API Platform génèrent tout : routes, validation, sérialisation). Dès qu'il y a une logique métier qui dépasse le CRUD (calcul de montant, vérification de droits d'achat, appel à un service externe, cookie, etc.), on écrit un contrôleur classique dans src/Controller/Api/.

Interfaces transverses (important à comprendre !)

Deux interfaces dans src/Entity/ gouvernent toute la sécurité des ressources "privées" :

  • OwnableInterface (getOwner(): ?User) : dit "cette ressource appartient à cet utilisateur". Utilisée par OwnershipVoter pour répondre à "ai-je le droit de voir/modifier/supprimer CET élément précis ?".
  • ScopedToOwnerInterface extends OwnableInterface (+ getOwnerPath(): string) : en plus, dit "et quand on liste la collection, filtre-la pour ne montrer que les miennes". Utilisée par OwnershipCollectionExtension pour modifier la requête SQL de la GetCollection.

Review n'implémente QUE OwnableInterface (pas ScopedToOwnerInterface) car la liste des avis doit rester visible par tout le monde — seule l'édition/suppression est réservée à l'auteur ou à un admin. C'est l'exemple à connaître par cœur avant de créer une nouvelle entité "à moitié privée".

5. Comment API Platform + la sécurité s'articulent

Sur chaque entité, l'attribut #[ApiResource(...)] déclare :

  • les opérations exposées (GetCollection, Get, Post, Put, Delete),
  • une expression security par opération (évaluée par le ExpressionLanguage de Symfony, avec accès à object, previous_object, is_granted(...)),
  • parfois un processor (classe qui intercepte l'écriture, voir §7) ou un securityPostDenormalize (règle vérifiée APRÈS que les nouvelles valeurs envoyées par le client ont été appliquées à l'objet — utile pour empêcher un changement de statut interdit, voir Game).

Trois couches de sécurité se combinent, dans cet ordre :

  1. config/packages/security.yaml → access_control : règles globales par préfixe d'URL (ex : ^/api exige d'être authentifié, sauf exceptions explicites comme /api/login, /api/register, les GET sur /api/games, /api/categories, /api/reviews).
  2. security sur chaque #[ApiResource]/opération : règle fine par ressource (ex : "seul un admin peut créer une catégorie").
  3. Les Voters (src/Security/Voter/) : logique d'autorisation réutilisable sur un objet précis.
Voter Attribut(s) Vérifie que...
OwnershipVoter OWNER_VIEW, OWNER_EDIT, OWNER_DELETE l'utilisateur connecté est le getOwner() de la ressource
GameVoter GAME_MANAGE l'utilisateur est le développeur propriétaire du jeu
GameVersionVoter GAME_VERSION_MANAGE l'utilisateur est le développeur propriétaire du JEU PARENT de la version
DeveloperProfileVoter DEV_PROFILE_MANAGE l'utilisateur est le titulaire du profil développeur

ROLE_ADMIN n'est jamais géré dans les Voters eux-mêmes : il est ajouté explicitement à côté dans chaque expression security, ex. "is_granted('ROLE_ADMIN') or is_granted('OWNER_VIEW', object)". Ce choix garde chaque Voter simple et à responsabilité unique — n'oublie jamais le is_granted('ROLE_ADMIN') or ... quand tu ajoutes une nouvelle opération sur une ressource "privée".

Filtrage automatique des collections (src/Doctrine/)

Deux extensions Doctrine modifient la requête SQL générée par API Platform avant qu'elle ne parte en base, pour appliquer des règles impossibles à exprimer avec un simple security (qui s'applique après coup, item par item) :

  • OwnershipCollectionExtension : pour toute entité ScopedToOwnerInterface, ajoute automatiquement WHERE <ownerPath> = :current_user (sauf si l'appelant est admin). C'est pour ça qu'un GetCollection sur /api/orders ne renvoie jamais les commandes des autres, sans qu'aucun contrôleur n'ait à écrire cette clause.
  • GameVisibilityExtension : cas spécial de Game, avec 3 vues différentes (games_public, games_developer, games_admin) et une politique dédiée dans App\Security\GameVisibilityPolicy (catalogue public = uniquement approved, espace développeur = ses propres jeux tous statuts, espace admin = tout).

Point clé pour un nouveau contributeur : si tu ajoutes une entité "privée" (liée à un seul utilisateur), fais-la implémenter ScopedToOwnerInterface et donne-lui un getOwnerPath() correct — sinon sa GetCollection fuitera les données de tout le monde vers tout le monde.

6. Authentification : JWT + refresh token

POST /api/login  (email, password)
   │
   ├─► JWT (access token, 2h — voir lexik_jwt_authentication.yaml `token_ttl`)
   │      renvoyé dans le corps JSON, à mettre dans l'en-tête
   │      Authorization: Bearer <jwt> sur chaque appel /api/*
   │
   └─► Cookie HttpOnly "refresh_token" (30 jours, path=/api)
          jamais lisible en JS (protection XSS), utilisé UNIQUEMENT par :

POST /api/token/refresh   (pas de body, le cookie suffit)
   └─► nouveau JWT + le cookie "refresh_token" est "tourné" (rotation :
        nouvelle valeur aléatoire + nouvelle expiration à chaque appel,
        pour qu'un token volé et rejoué après une rotation soit déjà mort)

POST /api/logout
   └─► supprime le refresh token en base + efface le cookie

Fichiers impliqués : AuthController (login/register/logout), RefreshTokenController (refresh), App\Security\RefreshTokenCookie (nom du cookie centralisé), App\Entity\RefreshToken.

⚠️ Piège classique : le nom du cookie (RefreshTokenCookie::NAME, actuellement refresh_token) doit être STRICTEMENT identique à token_parameter_name dans config/packages/gesdinet_jwt_refresh_token.yaml. Si tu renommes l'un sans l'autre, /api/token/refresh cesse de trouver le cookie et répond systématiquement "Invalid or expired refresh token".

Il n'existe aucune route publique pour créer un compte admin (par design, voir src/Command/PromoteUserCommand.php). Pour promouvoir un utilisateur :

php bin/console app:user:promote email@example.com admin

7. Les "State Processors" (src/State/)

API Platform désérialise le JSON entrant directement dans l'entité, ce qui est dangereux si on laisse le client remplir n'importe quel champ (ex : user_id, status). Les processeurs interceptent l'écriture pour corriger/compléter l'objet avant la persistance :

  • CurrentUserProcessor : force le champ propriétaire (user, reporter...) à l'utilisateur JWT courant. Branché sur Favorite, Review, Report, Download, BrowserSession.
  • GameCreateProcessor : à la création d'un Game, vérifie le rôle métier "Developer", récupère le DeveloperProfile de l'appelant, force le statut à Draft, et fait lui-même le persist()/flush() (nécessaire ici car API Platform ne sait pas encore à quelle relation rattacher l'objet avant ce traitement).

Règle à retenir : dès qu'un champ d'une entité ne doit JAMAIS être choisi par le client (propriétaire, statut initial, montant...), la bonne réponse n'est pas de le retirer du denormalizationContext (groupe :write) seulement — il faut aussi vérifier qu'aucun processeur ne le laisse passer tel quel, ou en écrire un.

8. Achats et paiements (le flux le plus sensible du projet)

1. POST /api/checkout  { game_id, method, phone }
   (CheckoutController)
   ─► vérifie : jeu existant + approuvé + payant, méthode supportée
      (Wave / Orange Money / YAS), téléphone au format sénégalais
   ─► calcule le MONTANT côté serveur à partir du prix réel du jeu
      (le client ne peut jamais envoyer un montant)
   ─► crée Order + OrderItem + Payment, tous en statut "Pending"
      dans une transaction Doctrine (wrapInTransaction)
   ─► appelle PaymentProviderInterface::initiate() : requête HTTP vers le
      prestataire externe, récupère une éventuelle checkout_url

2. Le joueur finalise le paiement côté prestataire (app Wave, etc.)

3. Le prestataire notifie de façon ASYNCHRONE :
   POST /api/webhooks/payments/{provider}
   (PaymentWebhookController — route PUBLIQUE, sécurisée par signature HMAC)
   ─► vérifie la signature (PaymentWebhookVerifier, HMAC-SHA256,
      un secret différent par prestataire)
   ─► vérifie l'idempotence via webhookEventId (un webhook rejoué ne
      change pas deux fois l'état)
   ─► met Payment + Order au statut Paid ou Failed

4. Le frontend peut interroger GET /api/payments/{id} (PaymentStatusController)
   pour du polling en attendant la confirmation.

5. GET /api/games/{id}/download (DownloadController)
   ─► vérifie que le jeu est gratuit OU qu'il existe une Order+Payment
      "Paid" pour CET utilisateur et CE jeu avant de renvoyer le lien
   ─► journalise le téléchargement dans un Download

Ne jamais faire passer un Payment/Order à "Paid" ailleurs que dans PaymentWebhookController : c'est la seule source de vérité, précisément parce qu'elle est protégée par la vérification de signature. Un bouton "j'ai payé" côté client, ou un changement de statut dans CheckoutController, casserait cette garantie.

9. Mettre en route le projet (checklist)

Cet export ne contient que src/ et config/. Pour lancer le projet localement il faut, dans l'ordre :

  1. composer require symfony/framework-bundle api-platform/core doctrine/orm doctrine/doctrine-bundle doctrine/doctrine-migrations-bundle lexik/jwt-authentication-bundle gesdinet/jwt-refresh-token-bundle nelmio/cors-bundle (+ les bundles listés dans config/bundles.php).
  2. Créer un .env.local avec au minimum :

- DATABASE_URL (PostgreSQL recommandé, voir identity_generation_preferences dans doctrine.yaml)

- JWT_SECRET_KEY, JWT_PUBLIC_KEY, JWT_PASSPHRASE (générer une paire de clés : php bin/console lexik:jwt:generate-keypair)

- APP_PUBLIC_URL (utilisée par PaymentProvider pour construire l'URL de callback webhook)

- PAYMENT_WAVE_URL / PAYMENT_WAVE_TOKEN / PAYMENT_WAVE_WEBHOOK_SECRET (idem pour ORANGE_MONEY et YAS) — sans ces variables, l'achat d'un jeu payant échoue proprement avec un message "prestataire non configuré côté serveur".

  1. php bin/console doctrine:database:create
  2. php bin/console doctrine:migrations:diff puis doctrine:migrations:migrate (aucune migration n'est fournie dans cet export, il faut les régénérer depuis les entités).
  3. php bin/console app:user:promote <ton-email> admin après avoir créé un compte via /api/register, pour avoir un accès admin de test.
  4. Le CORS est déjà configuré pour localhost/127.0.0.1 (nelmio_cors.yaml) : pense à ajouter le domaine de prod le jour du déploiement (le fichier contient un commentaire à cet effet).

10. Conventions à respecter en ajoutant du code

  • Une nouvelle ressource "CRUD simple" → nouvelle entité avec #[ApiResource], groupes de sérialisation nom:read / nom:write, et si elle est privée : implémenter ScopedToOwnerInterface + OwnershipCollectionExtension s'en charge automatiquement.
  • Une nouvelle règle d'autorisation qui dépend de plusieurs entités (ex: "propriétaire via une relation") → un nouveau Voter dans src/Security/Voter/, sur le modèle de GameVersionVoter.
  • Une logique métier qui écrit plusieurs entités liées, appelle un service externe, ou a des effets de bord (cookies, emails...) → un contrôleur classique dans src/Controller/Api/, jamais dans l'entité.
  • Un champ qui ne doit jamais être choisi par le client → le retirer du groupe :write ET vérifier/écrire un State Processor qui le fixe côté serveur.
  • Toujours ajouter is_granted('ROLE_ADMIN') or ... en tête des expressions security d'une ressource privée, sauf besoin explicite contraire.
  • Le style du projet est commenté en français, avec des docblocks qui expliquent le *pourquoi* (la règle métier, le risque évité) plutôt que le *quoi* (que le code dit déjà) — garde cette convention pour rester cohérent avec l'existant.
